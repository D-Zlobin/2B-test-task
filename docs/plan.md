# План разработки приложения для управления объектами и задачами

## 1. Цель

Создать веб-приложение на React + TypeScript с использованием Supabase, в котором постановщики управляют объектами и задачами, а исполнители работают только со своими задачами. Все ограничения доступа, переходы статусов и сохранение истории должны обеспечиваться на уровне базы данных, а не только интерфейсом.

## 2. Предлагаемая архитектура

- **Frontend:** React, TypeScript, Vite, React Router, официальный клиент `@supabase/supabase-js`.
- **Backend:** Supabase Auth, PostgreSQL, Row Level Security (RLS), хранимые функции и триггеры.
- **Аутентификация:** вход по email и паролю; открытая регистрация в интерфейсе отсутствует.
- **Конфигурация:** в клиент передаются только публичный URL Supabase и anon key. Service role key используется только при необходимости в защищённой серверной среде и не добавляется в репозиторий.
- **Миграции:** схема, функции, RLS-политики и права доступа оформляются как воспроизводимые SQL-миграции.

Сначала реализуется модель данных и серверные ограничения безопасности, затем интерфейс. Скрытие кнопок в React считается дополнительным удобством, но не механизмом защиты.

## 3. Модель данных

### `profiles`

Профиль связан с пользователем Supabase Auth:

- `id` — UUID, ссылка на `auth.users`;
- `role` — `manager` (постановщик) или `executor` (исполнитель);
- отображаемое имя — опционально для удобства интерфейса;
- дата создания.

Профили и роли создаются или изменяются только администратором проекта. Пользователь не может самостоятельно повысить свою роль через API.

### `objects`

- `id` — UUID;
- `name` — название;
- `address` — адрес;
- `created_by` — автор;
- `created_at`, `updated_at`, `deleted_at`.

### `tasks`

- `id` — UUID;
- `title` — название;
- `description` — описание;
- `object_id` — ссылка на объект;
- `assignee_id` — назначенный исполнитель;
- `author_id` — постановщик;
- `status` — `new`, `in_progress`, `in_review`, `accepted`, `rework`;
- `created_at`, `updated_at`, `deleted_at`.

При создании задачи статус всегда устанавливается в `new`, автор определяется по текущему пользователю, а исполнитель должен иметь роль `executor`. Значения полей проверяются ограничениями базы: обязательные поля, корректный статус и допустимые ссылки.

### `task_status_history`

- `id` — UUID;
- `task_id` — ссылка на задачу;
- `from_status` — предыдущий статус, `NULL` при создании;
- `to_status` — новый статус;
- `changed_by` — пользователь, выполнивший действие;
- `comment` — комментарий, если передан;
- `created_at`.

При создании задачи сохраняется начальная запись о переходе в `new`. Для каждого последующего перехода создаётся отдельная запись. Прямые вставки, изменения и удаления истории через клиентский API запрещены.

Удаление объектов и задач является мягким: запись получает `deleted_at`, исчезает из интерфейса и результатов API, но остаётся в базе вместе с историей. Восстановление через интерфейс не предусмотрено. Объект нельзя удалить, пока у него есть хотя бы одна неудалённая задача. Это исключает потерю истории и неявное каскадное удаление данных.

## 4. Правила доступа и безопасность базы

### Общие правила

- RLS включается для всех таблиц приложения.
- Доступ анонимных пользователей к данным запрещён.
- Политики явно разделяют `SELECT`, `INSERT`, `UPDATE` и `DELETE`.
- Дополнительно к RLS настраиваются права SQL: запрет RLS не заменяется лишними выданными привилегиями.
- В проверках используется `auth.uid()` текущего пользователя; идентификатор пользователя и роль не принимаются от клиента как доверенные данные.
- Для функций с повышенными правами задаётся безопасный `search_path`, а доступ к ним выдаётся только необходимым ролям.

### Объекты

- Постановщик видит, создаёт, редактирует и удаляет все объекты.
- Исполнитель видит только объекты, в которых существует хотя бы одна назначенная ему задача.
- Исполнитель не может создавать, изменять или удалять объекты.

### Задачи

- Постановщик видит все задачи, создаёт, редактирует и удаляет их, назначает исполнителя.
- Исполнитель видит только задачи, где `assignee_id = auth.uid()`.
- Исполнитель не может создавать или удалять задачи, менять объект, автора, исполнителя или другие рабочие поля.
- Статус задачи нельзя менять прямым обновлением таблицы: все переходы выполняются только через защищённую хранимую функцию.

### Профили

- Пользователь может читать собственный профиль, но не может менять свою роль.
- Постановщик может получать список исполнителей для назначения задач.
- Для отображения имён в доступных задачах и истории выдаются только необходимые данные, без открытия лишней информации о пользователях.

## 5. Переходы статусов и история

Создаётся хранимая функция `change_task_status(task_id, new_status, comment)`. Она выполняется атомомарно:

1. Блокирует выбранную задачу от конкурентных изменений.
2. Проверяет, что пользователь аутентифицирован и имеет доступ к задаче.
3. Проверяет роль пользователя и, для исполнителя, совпадение `assignee_id` с `auth.uid()`.
4. Проверяет текущий и новый статус по матрице разрешённых переходов.
5. Требует непустой комментарий при переводе `in_review` в `rework`.
6. Обновляет статус задачи.
7. Добавляет запись в историю с автором, временем, старым и новым статусом и комментарием.
8. Возвращает обновлённую задачу либо понятную ошибку без частичного сохранения изменений.

Матрица переходов:

| Текущий статус | Новый статус | Кто может выполнить |
| --- | --- | --- |
| — | Новая | Постановщик при создании задачи |
| Новая | В работе | Назначенный исполнитель |
| В работе | На проверке | Назначенный исполнитель |
| На проверке | Принята | Постановщик |
| На проверке | На доработке | Постановщик, комментарий обязателен |
| На доработке | В работе | Назначенный исполнитель |

Любой другой переход отклоняется базой. Дополнительный триггер защищает статус и историю от обхода хранимой функции прямыми запросами.

## 6. Экраны и пользовательские сценарии

### Вход

- Форма email и пароля, состояния загрузки и ошибки входа.
- Выход из аккаунта.
- Восстановление сессии после обновления страницы.
- Перенаправление неаутентифицированного пользователя на вход.

### Список объектов

- Постановщик видит все объекты и действия создания, редактирования и удаления.
- Исполнитель видит только объекты со своими задачами и не видит действий управления.
- Предусмотрены загрузка, пустое состояние и отображение ошибок.

### Карточка объекта

- Название и адрес объекта.
- Список задач объекта с названием, исполнителем, статусом и датой создания.
- Для постановщика — создание и редактирование задач, выбор исполнителя, удаление задачи.
- Для исполнителя — только назначенные ему задачи без действий администрирования.

### Карточка задачи

- Все поля задачи, объект, автор, исполнитель, статус и дата создания.
- Кнопки только для разрешённых текущему пользователю переходов.
- Диалог возврата на доработку с обязательным комментарием.
- Хронология изменений статусов: автор, дата и время, переход, комментарий.
- После действия интерфейс обновляет задачу и историю; ошибки базы показываются пользователю.

### «Мои задачи»

- Отдельный экран исполнителя со всеми назначенными ему задачами независимо от объекта.
- Отображение статуса и объекта, переход в карточку задачи.
- Постановщику этот пункт можно не показывать, поскольку список всех задач доступен ему через объекты.

### Навигация и состояния интерфейса

- Маршруты защищены от неавторизованного доступа, но серверные проверки остаются основным барьером.
- Общие состояния: загрузка, пустой список, ошибка запроса, отсутствие доступа, несуществующая запись.
- Для деструктивных действий постановщика используется подтверждение.

## 8. План проверки

### Функциональные сценарии

1. Постановщик создаёт объект и задачу, назначает исполнителя; задача появляется со статусом «Новая» и начальной записью истории.
2. Назначенный исполнитель переводит задачу «Новая» → «В работе» → «На проверке».
3. Постановщик возвращает задачу на доработку с комментарием; исполнитель повторно берёт её в работу и отправляет на проверку.
4. Постановщик принимает задачу; дальнейшие переходы недоступны.
5. В истории корректно отображаются все переходы, авторы, время и комментарии.
6. Постановщик редактирует и удаляет объекты и задачи; удаление объекта с задачами блокируется.

### Сценарии безопасности через прямые запросы к API

- Исполнитель не видит чужие задачи и объекты без своих задач.
- Исполнитель не может создать, удалить или изменить чужую задачу, а также изменить служебные поля собственной задачи.
- Исполнитель не может управлять объектами.
- Назначенный исполнитель не может принять задачу или вернуть её на доработку.
- Постановщик не может выполнить переходы, предназначенные исполнителю.
- Нельзя пропустить статус, повторить переход или изменить статус напрямую в обход функции.
- Нельзя вернуть задачу на доработку без непустого комментария.
- Нельзя вставить, изменить или удалить запись истории через API.
- Пользователь не может изменить собственную роль.
- Два одновременных действия над одной задачей не приводят к потере истории или недопустимому итоговому статусу.
- Анонимные запросы не возвращают данные и не изменяют их.

## 10. Критерии готовности

- Все экраны из спецификации реализованы и работают с реальными данными Supabase.
- Доступные действия соответствуют роли и текущему статусу задачи.
- Полный рабочий цикл задачи и история изменений работают без ручных правок базы.
- RLS и проверки базы блокируют запрещённые операции при обращении в обход интерфейса.
- История защищена от изменения и удаления через клиентский API.
- Проект собирается без ошибок TypeScript, основные сценарии обеих ролей проверены.
- Приложение опубликовано, ссылка и тестовые доступы готовы к передаче; демонстрационные данные заполнены.
- GitHub-репозиторий содержит исходный код, воспроизводимые миграции и понятный README.
- Подготовлены пояснение для руководителя и список решений, допущений и невыполненных работ.
- Секретные ключи отсутствуют во frontend, репозитории и его истории.

## 11. Решения, принятые до реализации

Этот раздел фиксирует правила там, где спецификация допускает разные трактовки. Он является частью требований к реализации; в конце работы из него формируется список решений и допущений для заказчика.

### Роли и работа с задачами

- Задачу может принять или вернуть на доработку **любой постановщик**, а не только её автор: это следует из права постановщика видеть и проверять всё.
- Выполнять переходы исполнителя может только текущий назначенный исполнитель, даже если у другого исполнителя есть задачи на том же объекте.
- Статус «Принята» является конечным: повторно открыть задачу или вернуть её в работу нельзя. При этом постановщик сохраняет данное спецификацией право редактировать поля или удалить принятую задачу.
- Постановщик может редактировать название, описание, объект и исполнителя задачи в любом статусе. Автор, дата создания и статус обычным редактированием не меняются.
- Изменения обычных полей не создают записи в истории: спецификация требует историю только смены статусов.
- Название, объект и исполнитель обязательны для задачи, описание может быть пустым. Для объекта обязательны название и адрес. Обязательные строки не могут состоять только из пробелов.
- Комментарий можно приложить к любому переходу статуса, но только при возврате на доработку он обязателен. Комментарий из одних пробелов считается пустым.

### Переназначение и видимость

- Постановщик может переназначить задачу другому исполнителю в любом статусе; статус при этом не меняется.
- Сразу после переназначения прежний исполнитель теряет доступ к задаче и её истории, а новый получает доступ к задаче и всей предыдущей истории.
- Объект виден исполнителю, пока у него есть хотя бы одна неудалённая задача на этом объекте, включая принятую. После переназначения или удаления последней такой задачи объект исчезает из его списка, если других его задач там нет.
- Смена объекта у задачи сразу меняет видимость обоих объектов для исполнителя по тому же правилу.

### Удаление и сохранность истории

- Удаление объектов и задач мягкое: через защищённые функции выставляется `deleted_at`. Клиент не получает права произвольно менять это поле или физически удалять записи.
- RLS и запросы исключают удалённые записи из всех списков, карточек и проверок видимости.
- Удалённая задача и её история остаются в базе, но карточка становится недоступна через приложение и клиентский API. Восстановление не входит в первую версию.
- Объект можно удалить только при отсутствии неудалённых задач. Уже удалённые задачи не препятствуют удалению объекта и сохраняются в базе вместе со своей историей.
- Перед удалением интерфейс показывает подтверждение и объясняет, что действие нельзя отменить через приложение.

### История, даты и порядок записей

- Создание задачи считается переходом `NULL → new` и сохраняется в истории.
- Записи истории отображаются в хронологическом порядке от создания к последнему переходу; задачи в списках — сначала новые по дате создания.
- Время хранится в UTC как `timestamptz`, а в интерфейсе показывается в часовом поясе браузера пользователя с однозначной датой и временем.
- В истории фиксируется пользователь, выполнивший переход. Последующая смена имени профиля не переписывает сам факт действия; отображается актуальное имя пользователя.

### Пользователи и отображаемые имена

- Пользователи и их роли заводятся вручную в Supabase. Административного экрана управления пользователями, самостоятельной регистрации и смены роли через приложение не будет.
- Для всех демонстрационных пользователей заполняется отображаемое имя; в списках и истории показывается оно, а не внутренний UUID.
- Восстановление пароля и подтверждение email через письма не настраиваются для тестовой версии: тестовые пользователи создаются уже подтверждёнными.

### Интерфейс и объём первой версии

- Делается простая адаптивная вёрстка для компьютера и телефона без отдельной дизайн-системы.
- Поиск, фильтры, сортировка пользователем и пагинация не добавляются: для демонстрационного объёма достаточно стандартного порядка списков.
- После создания, редактирования или смены статуса данные явно обновляются. Постоянное realtime-соединение и автоматическая синхронизация открытых вкладок не требуются.
- В первую версию не входят уведомления, вложения, отдельные обсуждения задач, экспорт, восстановление удалённых записей и история редактирования обычных полей.

### Формат сдачи

- Приложение публикуется на **Vercel**, исходный код размещается в **публичном GitHub-репозитории** без секретов и реальных данных клиентов.
- Для руководителя выбирается **текст примерно на полстраницы**, а не видео: его проще хранить вместе с проектом и проверять перед сдачей.
- Подготавливаются три объекта и задачи, покрывающие все пять статусов. Передаются доступы одного постановщика и двух исполнителей; второй постановщик дополнительно используется при проверке прав, но его доступ не обязателен для демонстрации.
- Конкретные названия объектов, имена пользователей, логины и пароли являются наполнением демонстрации, а не открытыми продуктовыми вопросами. Секреты и доступы передаются отдельно от репозитория.

После принятия этих правил открытых продуктовых вопросов, блокирующих начало реализации, не остаётся. Если реализация выявит новое противоречие со спецификацией, решение добавляется в этот раздел до изменения поведения системы.
